# State coverage

What Grant Matcher covers in each of the 50 states and the District of Columbia, checked November 25, 2026. The 18 states whose pages are web pages were read again on November 26, 2026 (section (g)). The state-by-state research behind section (b) was done the same day with anonymous requests only (no accounts, keys, sign-ups or terms accepted). Part of it ran under the user agent `grant-matcher-research` before the project settled on `grant-matcher (github.com/RendellRich/grant-matcher)`. One batch of that research (Louisiana to North Dakota) retried with a browser-style user agent after a 403, which the rule below doesn't allow. Its notes mark Maine's funding page as read only that way, so nothing from that page is used, and no status or reason on this page rests on such a retry. The registry that the code reads is `grantmatch/states.py`; this page explains it.

**The rule.** A page is read only after the host's robots.txt, with the project's own user agent. If robots.txt keeps out this crawler, ClaudeBot or the path, if the terms bar automated access or commercial reuse (Grant Matcher is a paid product), if the site turns scripts away, or if neither can be confirmed, the page isn't used. For those sources this page keeps only the host and the reason. This rule was not met by all of the research: some pages were fetched before robots.txt or terms were read, including pages on hosts now blocked, and some rows in section (b) come from research that records no such check. For adeca.alabama.gov, agriculture.vermont.gov, the Louisiana arts division, cde.state.co.us, kansascommerce.gov and commerce.idaho.gov the research notes record that the content or cached copy was removed, and nothing here rests on it. For other blocked hosts the notes record no removal; their rows say why each is kept out and report nothing from its grant pages. Maryland, Massachusetts, Michigan, Missouri, Montana and North Dakota were rechecked on November 25 with the project's own user agent, robots.txt before the pages on each host; their rows report only what that recheck saw.

**Short answer.** Federal grants, private foundations, community foundations and the county list cover all 50 states and DC. State grant lists cover 14 states and DC (reading Illinois' list is paused, section (f)): Florida, California, Illinois, Iowa, Ohio, Washington, West Virginia, New Jersey, New York, the District of Columbia and Minnesota (two agencies only, not a statewide list) and, from web pages read on November 26, Arkansas, North Dakota and Wyoming (each its arts council only) and Maryland (a short list on one department's page). In the other 36 states the site says plainly that there is no state catalog yet. Of those 36: 3 have a machine-readable list that Ren decided on 2026-11-25 to leave out (Alaska, Hawaii, Pennsylvania), for 14 the grant pages checked are web pages or a dashboard, not a data file, and gave no list this project could build from (section (g)), 14 are **blocked** (robots.txt, terms or a refusal to scripts keep the key pages out), 3 had no current list anywhere the research looked, and 2 are **unchecked** (Massachusetts and Mississippi). County and city programs are hand-kept for some counties and cities in 9 states ([county-coverage.md](county-coverage.md)).

## (d) Refresh job

The weekly job approved on 2026-11-25 is `.github/workflows/refresh-states.yml` ("Refresh state lists"). It runs weekly, Mondays at 13:17 UTC (cron `17 13 * * 1`), and it can also be run by hand. One job on ubuntu-latest reads both lists (`python -m grantmatch.westvirginia --out build/westvirginia.json.gz --skipped build/skipped-westvirginia.json.gz`, and the same for `grantmatch.newjersey`), embeds them (`python -m grantmatch.embed programs`), and uploads six files to the data-latest release: `westvirginia.json.gz`, `westvirginia.npz`, `skipped-westvirginia.json.gz`, `newjersey.json.gz`, `newjersey.npz` and `skipped-newjersey.json.gz`. `tests/test_states.py` reads the file and checks the cron, the commands and the uploaded names against `grantmatch/states.py`.

Until its first run, West Virginia and New Jersey ship from the committed snapshots `data/westvirginia.json.gz` and `data/newjersey.json.gz`, made on November 25, 2026. `export_web.fetch()` asks the release for `westvirginia.json.gz`, gets a 404, and reads the file in `data/` instead (tested in `tests/test_states.py`). Until the job has published vectors, `program_vectors()` embeds the records during the export, as it already does for the hand-kept lists. A snapshot ages. `export_web` leaves out any call whose closing date is before the day of the export (`still_open()`, for every open-call state; Florida's catalog and the hand-kept lists keep their own rules), so expired calls stop showing, and the state tab says when its data was last updated. Calls the state adds after the snapshot don't appear until the job runs (or the snapshot is remade with `python -m grantmatch.westvirginia --out data/westvirginia.json.gz` and `python -m grantmatch.newjersey --out data/newjersey.json.gz`). On November 25 the New Jersey snapshot had 9 dated calls (the first closing December 4) and 22 rolling ones; West Virginia's 7 close between December 15, 2026 and June 30, 2027, except one ongoing.

**How new data reaches the site.** "Refresh state lists" is not in `deploy-site.yml`'s `workflow_run` list (that list names the federal, Florida, California, Illinois, Iowa, Ohio, Washington, foundations and funder website refreshes), and `deploy-site.yml` is unchanged, so the weekly job doesn't start a deploy itself. The next deploy picks the new files up, because the export reads the release at every deploy, and the federal refresh triggers one twice a day. So new West Virginia and New Jersey data reaches the site within about 12 hours of the weekly run. Until the job's first run, a remade snapshot also reaches the site on the next deploy (the deploy workflow's push paths don't include the two files, so pushing one starts no deploy); after that run the release copy is used instead.

Weekly means a call a state opens mid-week can show up to a week late. Closed calls still drop out at every site export, which runs several times a day, because `still_open()` checks each record's closing date against the export day, not the refresh day.

Later states join the same job as more lines in the two steps, so the job count doesn't grow with each state. A proposed version that runs New York, DC and Minnesota too is in [proposed-workflows/refresh-states.yml.txt](proposed-workflows/refresh-states.yml.txt) and isn't in use ([freshness.md](freshness.md)). Two workflow changes are still not made. First, `deploy-site.yml`: its push paths list `grantmatch/export_web.py` but not `grantmatch/states.py`, which the export now reads, so a change to the registry alone wouldn't rebuild the site until the next refresh-triggered deploy. Second, `skipped-report.yml`: until it changes, West Virginia and New Jersey stay out of the Friday skipped grants report, because it neither downloads their skipped lists nor passes their data files. The change, not made: add `-p 'skipped-westvirginia.json.gz' -p 'skipped-newjersey.json.gz'` to the first `gh release download`, `-p westvirginia.json.gz -p newjersey.json.gz` to the second, and `--westvirginia build/westvirginia.json.gz --newjersey build/newjersey.json.gz` to the `python -m grantmatch.skipped` line. `grantmatch/skipped.py` already takes those arguments and reads the two skipped lists when they are there (both come from `grantmatch/states.py`). Their registry entries have `"in_skip_report": False`, so the report doesn't call their files missing meanwhile; once `skipped-report.yml` downloads them, setting it to true makes the report say when a refresh failed to publish one. The report job's minutes don't change measurably (a few more seconds of download).

**Billed minutes.** Job times from `gh run view` for the recent successful runs of each existing state refresh, on ubuntu-latest (billed per job, rounded up to the minute):

| Refresh | Job time | Billed a run |
|---|---|---|
| Ohio | 50 to 58 s | 1 |
| Washington | 52 to 60 s | 1 |
| Iowa | 59 to 67 s | 1 to 2 |
| California | 64 to 81 s | 2 |
| Illinois | 142 to 158 s | 3 |

So the existing jobs take 50 to 158 seconds, 1 to 3 billed minutes a run. The new job hasn't run yet, so its time is an estimate. Illinois and Iowa are slower because they read a page per notice; California downloads a 6.6 MB file. The West Virginia and New Jersey adapters each make one small request (a 700 KB JSON list and a 7 KB CSV), like Ohio and Washington, but the job runs two of them and two embedding steps, so expect it near California's: about 60 to 90 seconds, **1 to 2 billed minutes a run**.

- **Weekly, as added:** about 4.3 runs a month, so **about 4 to 9 billed minutes a month**.
- **Rejected alternative, daily:** 30 to 62 billed minutes a month (2 minutes every day of a 31-day month is the top), for calls showing up within a day instead of within a week.

A deploy triggered by a refresh (`deploy-site.yml` build and deploy jobs) took 6 to 8 minutes on November 24, about 7 to 9 billed minutes. Adding "Refresh state lists" to deploy-site's `workflow_run` list would add about 30 to 40 billed minutes a month (210 to 270 if the job ran daily). It isn't needed, for the reason above: the next deploy picks the data up within about 12 hours. The job as added costs about 4 to 9 minutes a month.

**Arkansas, Maryland, North Dakota and Wyoming** (added November 26) are read by the same job with no workflow change: it takes its list from the registry (`grantmatch/refresh_states.py` runs every state whose refresh is weekly or not yet set). Their registry entries say `"refresh": None` and `"in_skip_report": False` until the job has read them once and `skipped-report.yml` downloads their files. A change to a page's shape makes that state's run fail, its last file stays, and the other states are still published. The Arkansas page is prose, so expect that to happen when its yearly dates are rewritten.

**Billed minutes added (estimate, not measured on a runner).** One local run of the four on November 26 asked for 4 robots.txt files and 12 pages, with 2 second pauses, in 23 seconds. On the runner each also needs its own embedding step (about 5 to 15 seconds to load the model and embed a few records). So:

| Job | Added a run | Added a month |
|---|---|---|
| `refresh-states.yml` | 45 to 90 seconds, usually 1 more billed minute | about 4 to 10 |
| `watch-pages.yml` (freshness check: 4 more source pages and the new call links, 2 seconds apart, inside its existing caps) | 0 to 1 billed minute | about 0 to 5 |
| `skipped-report.yml` and deploys | no measurable change | 0 |

About **4 to 15 billed minutes a month** in all. The proposed text files in [proposed-workflows/](proposed-workflows/) add the four states' skipped lists to the Friday report and update the refresh job's comments; neither is in use.

**What the cards can't say.** New York's grid has no link to a single opportunity (every card links the public search page and gives the Event ID), no description or award amount, and titles cut at 50 characters. Agencies are codes; only DOL01 is named, because the list itself spells it out. The State Comptroller publishes code lists as PDF files, which weren't downloaded. The District's tables don't say who may apply. Minnesota is two agencies, not the state.

**Freshness.** No job refreshes these three yet: they ship as read on November 25, 2026. Adding them to `refresh-states.yml` is a workflow change and costs Actions minutes, so it waits for Ren. They aren't in the Friday skipped grants report either (`"in_skip_report": False`).

## (f) Illinois: reading paused

**Reading Illinois' state list is paused pending the state's written OK (Ren's decision, 2026-11-25).** omb.illinois.gov and il.amplifund.com answer robots.txt with a web page, which the project's crawling rule treats as off limits, and the daily refresh had been reading them.

- **The switch** is the `"paused"` key of Illinois' entry in `grantmatch/states.py`. Removing it resumes reading.
- **What is not asked:** nothing on omb.illinois.gov or il.amplifund.com, not even robots.txt, by the adapter, the page watch, the freshness check or the website check, redirects included. The hand-kept Illinois programs come from other agencies' pages and are checked as before, under the crawling rule.
- **The daily job** (`refresh-illinois.yml`, unchanged) still runs. The adapter copies `illinois.json.gz` and `skipped-illinois.json.gz` from this project's own data-latest release, byte for byte, then the job embeds and uploads them as usual. If the published data can't be read or holds no calls, the run fails and uploads nothing. The job still uses its Actions minutes, and a successful run still starts a site deploy.
- **The data's date** is the `fetched_at` inside the file, which stops moving. The Illinois tab says reading is paused and gives that date, and the freshness check flags the data as old after 3 days. On 2026-11-25 the published file had last been uploaded at 23:21 UTC that day.
- **When it takes effect:** the job runs from main, so it keeps reading Illinois until this code is merged there. The date that stays on the tab is that of the last run before the merge.
- **Closed calls** with a deadline still drop out at each site export. A call with no end date stays until reading resumes.
- A request to the state for written permission has been drafted and not sent.

## (g) The 18 web-page states, read November 26, 2026
